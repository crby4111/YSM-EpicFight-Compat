# Minecraft 1.20.1 正式使用验收标准 v1

制定日期：2026-10-27。适用范围：当前 `mc/1.20.1` 分支的官方 YSM × Epic Fight 兼容模组，以及随其交付的本机外部动作预览器。

**正式可用 = 下列必验项全部通过，受支持模型实际能正常游玩，且没有未解决的阻断问题。** 编译成功、单元测试通过、离线矩阵正常均不能替代游戏验收。达到标准后仍由用户决定正式发布及版本号。

## 1. 先冻结验收对象

每次验收先填写记录，不能用宽泛的依赖版本范围代替实际安装版本：

| 项目 | 必填内容 |
| --- | --- |
| 模组 | 候选包名称、SHA-256、源码提交及未提交补丁摘要 |
| 环境 | Minecraft 1.20.1、Forge、官方 YSM、Epic Fight、YSM-Mapping-API 的实际版本 |
| 附加模组 | 必需与可选模组清单；声称支持的可选集成分别测试 |
| 模型 | 模型标识、版本、源文件校验、骨骼数、贴图与初始换装状态 |
| 规则 | 完整规则文件及资源包校验；默认、覆盖、额外层三套基准配置 |
| 机器 | CPU、GPU、内存、Java 参数、分辨率、视距及图形设置 |
| 证据 | 日志、录像、配置、测量数据及复现步骤的本地路径 |

首轮必验模型：默认简单模型、M042、A3、Phainon V4。后三者使用现有本地测试副本，不修改原模型来绕过适配问题。至少覆盖普通模型及超过旧骨骼容量的复杂模型；增加一个自有合成夹具检查 4096 骨骼边界，超过边界必须明确拒绝并安全回退。

支持声明以实际验收的组合为准，不能把单个模型通过扩大成“所有 YSM 模型兼容”。文件夹模型和 `.ysm` 包分别检查；需要合法样本而暂缺样本时记为未测。未通过的模型只能明确留在实验支持清单，不能计入本轮正式支持。

## 2. 功能和画面门槛

| 编号 | 必验内容 | 通过条件 |
| --- | --- | --- |
| F01 默认行为 | 启用规则但无覆盖、额外层 | 战斗渲染由 EF 驱动身体；不暗中按移动/战斗硬切动作来源。退出 EF 接管后，普通模式仍由官方 YSM 正常显示 |
| F02 自选覆盖 | 移动、攻击、受伤、持物/使用、视角、模型及 EF 动作条件；与/或/非和优先级冲突 | 结果与配置一致；攻击和受伤没有额外硬编码否决。规则落选时不推进其控制器生命周期；规则顺序与优先级有确定结果 |
| F03 额外动作 | EF + 额外层、覆盖 + 额外层、多个额外层 | 同时生效，骨骼遮罩和旋转/位置/缩放通道不越界；覆盖与加算、权重、淡入淡出结果正确，非目标骨骼不被重置 |
| F04 原生特色 | 头发、裙摆、肩部、披风/尾巴、表情、眼睛及模型自带换装 | 与同输入下官方 YSM 的正常外观对照；需要隐藏的组件正确隐藏，无额外肢体、漂浮换装件、贴图丢失、身体塌缩或初始化遗漏；物理不重复计算 |
| F05 时钟与状态 | 独立、原生共享、EF 进度三种适用时钟；clip、authored_state、controller 来源 | 各来源只接受其声明支持的时钟；控制器切换、过渡、数值初始化、退出再进入正确；同实体同控制器同采样时刻只推进一次，不同玩家/视角互不串状态 |
| F06 回退和诊断 | 空控制器状态、无效来源、未支持控制器结构、无效查询与规则错误 | 空姿态保持 EF；不可用来源按已声明规则回退；输出指出实际使用来源及具体原因。不得把数值默认值伪装成完整支持，不得卡在 T 姿势、黑屏或崩溃 |
| F07 平滑切换 | EF 接管开关、动作打断、模型/贴图切换、死亡重生、视角切换 | 不能出现可复现的一帧绑定姿态、错误翻转、持续穿身、附属物爆散或旧模型残影；配置声明的过渡时长符合预期 |
| F08 朝向与持物 | 游泳、爬行、飞行、梯子；双手武器、盾牌、弓/弩、食用/饮用 | 头部视线与身体朝向合理，游泳/飞行无重复旋转；武器、手部及背负位置正常，切换后不留下错位 |
| F09 第一人称 | 原版及 EF 使用到的第一人称渲染路径 | 手臂、持物、使用与攻击动作正常；无双手重复、缺失、穿相机或第二个身体；切回第三人称无残留状态 |
| F10 游戏机制 | 连击、蓄力、防御、闪避、受击/击倒、目标命中 | 动作覆盖只改变声明的表现，不改变 EF 伤害、攻击窗口、技能消耗、实体碰撞及同步逻辑；效果/声音不因采样重复触发 |

所有必验模型至少执行：站立、走路、奔跑、潜行、跳跃/下落、游泳/水中停留、爬行、梯子、创造飞行/鞘翅飞行、转头、近战连击、持盾防御、远程使用、受击、死亡重生。不存在的模型专属部件可预先注明不适用，通用动作不能以“不适用”跳过。

动作画面回归先于长时间稳定性验收执行。修改骨骼转轴或姿态重定向时，记录实际检查的动作目录及起始、关键旋转、结束姿态，核对左右肩臂连接和肘腕连续性；同时保留正常待机/移动作为对照。已报告的 M042 `guard*`、`relentless_combo`、`sweeping_edge` 纳入定向回归，不得用单个待机画面或有限矩阵检查代替。标准骨架和声明支持的扩展骨架分别检查，外部预览与游戏结果分别登记；抽样记录只能证明所列样本。

每种稳定状态至少观察 10 秒；每种切换连续重复 20 次。至少做以下交叉场景：

1. 连击中触发模型动作覆盖，同时保留披风/尾巴额外层。
2. 游泳 ↔ 站立 ↔ 受击，反复打断并恢复默认 EF。
3. 两条覆盖条件同时成立，再分别撤销；检查优先级和退出状态。
4. 同一控制器供多个骨骼遮罩使用；两名玩家同时使用不同状态。
5. 淡入淡出过程中修改规则、切换视角或模型。

穿模判定使用同模型的官方 YSM 表现作参考。原模型本来存在的轻微穿模应记录；本模组新增的持续穿身、明显关节断裂或普通视角可见的严重变形属于阻断项，不能用“原模型复杂”豁免。

## 3. 稳定性、多人和性能门槛

下列数量和百分比是本项目从现在起采用的验收目标，并非 alpha.3 已测成绩。

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| R01 生命周期 | 冷启动与热缓存启动各 3 次；资源重载、模型/贴图切换、进出世界、维度切换、死亡重生各 20 次 | 无崩溃、死锁、持续空白、旧贴图、跨玩家状态污染；失败后仍可切回可用模型 |
| R02 长时间游玩 | 连续 2 小时，包含至少 30 分钟战斗及上述移动/切换场景 | 无模组导致的崩溃、持续错误刷屏、动作停止更新或可复现的资源持续增长 |
| R03 多人 | 局域网集成服务器、独立服务器各至少 2 个真实客户端；观察自己与对方 | 模型、贴图、规则适用结果符合已声明的配置归属；攻击和切换可见；断线重连/维度切换/对方更换模型后不串状态；服务端不加载客户端渲染类 |
| R04 规则与资源热更新 | 有效规则、损坏 JSON、缺失片段、错误控制器和资源包重载 | 有效配置生效；无效更新不破坏上一份有效配置；首次配置无效则安全使用默认行为并给出定位信息；不需反复重启恢复 |
| R05 输入和缓存异常 | 超限模型、损坏包、损坏缓存、源文件变化、过期远程缓存 | 按模型隔离失败、边界校验有效、缓存正确失效或重建；不覆盖原模型、游戏存档和用户资源 |
| R06 资源释放 | 预热后做 100 次模型/资源切换，分 5 组记录 | 在相同稳定场景测堆内存、纹理/GL 资源数、缓存项数；后 3 组能回到稳定区间。堆内存使用相同 GC 观察条件，末组不超过预热稳定值 110%；未解释的逐组增长判失败 |
| R07 性能 | 固定硬件/画质/路线，单人及 4 个同时动作的可见角色；每组预热 60 秒、采样 180 秒、做 3 轮 | 以同候选构建关闭规则为 A，默认规则和完整规则分别为 B/C。先单列关闭规则本身是否有卡顿；B/C 中位帧耗时增加 ≤10%，P95 增加 ≤15%；无归因于规则系统的 ≥100ms 重复卡顿。冷加载另测，不混入稳态统计 |

性能基准记录绝对 FPS/帧耗时和相对变化。测试画质使用 1080p、关闭光影，并固定视距、实体数、帧率限制与同步设置；具体值写入记录。宣称支持的机器在所承诺的画质下应达到稳定可玩表现；不能通过压低已经很卡的基准来满足相对门槛。复杂模型触发 CPU 蒙皮时必须单独测量，不得沿用简单模型结果。

可选集成（例如 ParCool）只有在声明正式支持时才进入额外必验矩阵。未安装时仍需检查基础功能；已声明支持的集成不能只验证“缺失时不崩溃”。

## 4. 外部预览器门槛

| 编号 | 内容 | 通过条件 |
| --- | --- | --- |
| V01 可操作 | 选择模型/贴图、动作、控制器、条件、规则、额外资源 | 列表来自实际模型；错误输入能定位原因；播放/暂停、拖动/逐帧、速度、循环及视角正常 |
| V02 与模组一致 | 相同候选版本、模型、规则、查询输入及采样时钟 | 默认 EF、覆盖和额外层各至少一例，与游戏采样的局部骨骼位置、旋转和缩放逐项对照；误差目标为位置 ≤0.001 方块、旋转角差 ≤0.5°、缩放 ≤0.001。不能仅比较“矩阵有限” |
| V03 画面可信度 | 外观初始化、组件隐藏、贴图、朝向、附属物 | 对受支持模型不出现错误组件全显示。确定性姿态与游戏对照；物理比较需相同初始状态、时间步与随机种子，否则标为近似，不能声称完整重建 |
| V04 安全与边界 | 启动、导入导出、退出、异常模型 | 不启动游戏、不修改原模型或游戏配置；保持本机服务范围；清楚区分“精确支持”“近似”“不支持”，不能默默补零后显示为通过 |

预览器对持物、光影或某些游戏事件没有实现时，应明确标为未重建。未重建内容不能成为该内容游戏内通过的证据。V02 的完整对照暂不可执行时记为未测，不能降成仅通过演示模型。

## 5. 工程与交付门槛

- 同一候选源码完成编译、完整测试、集成检查及分发验证；失败数为 0。跳过项逐项说明原因，与必验功能有关的跳过必须另补证据。
- 验收必须使用交付 JAR 的同一校验值。影响姿态、状态或渲染的代码修改后重跑对应游戏矩阵；跨越多个模块的修改重跑全量。重新打包后至少复核内容与校验，不能拼接不同构建的通过记录。
- 安装说明给出准确依赖组合、配置位置、模型 ID/控制器查找方式、三类规则示例、重载方法和回退步骤。普通使用只需安装与配置，不需要修改模型文件或 Java 源码。
- 验证关闭规则、移除模组或恢复旧配置后能回到原来可用状态；不破坏存档、账号数据及原模型。发布包不包含官方 YSM JAR、未获分发许可的模型或私人测试资产。
- 交付物包含候选 JAR、示例配置、已测组合、已知限制、校验清单、逐项验收记录及必要录像/日志索引。

## 6. 判定规则

记录只使用 `PASS / FAIL / NOT_RUN / N/A`。`N/A` 必须在执行前说明为何不适用；没有证据就是 `NOT_RUN`，不可默认为通过。

以下任一情况阻止正式使用判定：崩溃/死锁、数据损坏、常用动作失败、严重新增变形、组件错误全显示、持物/第一人称严重异常、多人状态污染、游戏机制变化、长期泄漏、性能门槛失败，以及必验项未测。

轻微且不影响使用的缺陷可登记为非阻断问题，附范围、复现方法和临时处理办法；不能把必验项临时改成可选来通过。改变验收范围或阈值必须先说明理由并形成新版本，不能在测试失败后静默下调。
