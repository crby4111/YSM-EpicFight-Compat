# Minecraft 1.20.1 后续开发计划

更新日期：2026-10-29。适用分支：`mc/1.20.1`。

目标是让用户保留模型特色、正常游玩并能自行选择动作来源。开发顺序以实际影响为准：
先修看得见的错误，再补控制器和渲染衔接，随后完善预览与配置体验，最后收敛正式发布条件。

## 1. 当前基线与已知边界

代码基线为 `1.1.0-alpha.6`，提交 `ee5f4aaf2688659e6b88c132db16c6dd50d1c2b5`。
该提交是开发成果，不代表正式使用验收已经通过。

| 内容 | 当前状态 | 后续重点 |
| --- | --- | --- |
| 默认 EF、自选覆盖、额外动作 | 已实现条件选择、骨骼/通道遮罩、权重与播放时钟 | 根据真实模型反馈修正组合与切换缺陷，改善配置体验 |
| 原生控制器 | 已接入支持的 `ysm-builtin` 槽位、脚本提供者、关联装备/持物栈与暂停等状态 | 明确剩余状态图、脚本和事件输出边界，按实际需求补齐 |
| 外观与物理层 | 已共享 authored 采样、时间线与结果，处理关联层合成 | 检查真实模型中的初始化、物理连续性和状态释放 |
| 姿态修复 | 已加入肩肘支点、Root 缩放传递、头部后处理及身体朝向衔接修正 | 当前版本的实机画面仍需确认，尤其游泳、转头、持物与切换 |
| 问题采集 | 已实现 F9、动作/骨骼快照、截图及相关日志保存 | 真实客户端采集尚待确认；逐步补充排查所需信息 |
| 外部预览 | 已支持受控运动输入、控制器选择及记录帧查看 | 补缺失输入、状态对照与回放能力，清楚展示未重建部分 |

alpha6 完成了构建、分发检查、34 项针对检查、4 项本机接口检查及原创夹具的记录帧导入核对。
本版本没有完成 Minecraft 实机、多人、长时间运行或性能验收。
记录帧查看直接使用保存的蒙皮结果，不等于完整执行了原来的游戏过程。

以下边界不能用“代码已经写了”来消除：

- M042 等模型的手臂修正已有代码，仍需当前 JAR 在游戏中的表现确认。
- 游泳头发穿模的具体剩余成因尚未确定；可能来自兼容层，也可能需要模型专属修正规则。
  先定位实际受影响的骨骼、片段和变换，不能提前认定统一加一段头发旋转就能解决。
- 控制器递归引用仍不支持；声音、粒子和同步输出不会因选择控制器而自动重放。
- 部分查询、完整控制器/物理历史、随机状态、游戏摄像机、装备和光影不在当前记录帧重建范围内。

## 2. 开发原则

1. **保持用户决定权。** 默认由 EF 执行动作；覆盖和额外层由用户条件选择。
   不另外写死“攻击时一定不能使用模型动作”等隐藏否决。
2. **保持单一身体所有权。** 每帧一个基础身体姿态，额外层按明确的范围、通道和顺序组合。
   空控制器、缺失片段和不支持的输入要给出原因并安全保留 EF。
3. **保持原生特色的连续性。** 区分外观显隐、身体动作、物理和事件，避免重复初始化、推进或输出。
4. **按实际问题修改。** 先确定生效的模型、控制器、片段和骨骼路径；保留用户原模型、存档和运行日志。
   模型专属修正使用可选择的配置或副本，不通过改动原模型掩盖兼容层缺陷。
5. **保持官方集成边界。** 继续使用官方 YSM 与 Mapping API；不增加私有扫描、运行时混淆名称或私有反编译依赖。
   普通模式仍由官方 YSM 渲染，不改动 EF 的伤害、碰撞、技能等玩法逻辑。

## 3. 阶段 A：优先收敛实际画面问题

**优先级最高。下一轮先从用户实际发现的问题推进，不要求用户执行庞大的测试清单。**

### 要开发和修复的内容

- 接收实际游玩中的 F9 报告，关联 JAR 摘要、模型、动作、时间、视角、规则与骨骼结果。
  如果报告没有采到姿态、截图或关键状态，明确指出缺失内容，再补采集代码。
- 优先处理手臂离体、错误身体/头部朝向、严重穿模、重复部件和持物错位。
  对 `guard*`、连招、横扫、游泳抬头等已报告场景保留具体问题条目。
- 对游泳头发问题，追踪头部、发根、上段发束和物理链的实际变化，区分动画原有穿模、
  重复旋转、错误继承、错误加载路径与兼容层新增偏差，再决定修改位置。
- 在相应模型确有需要时加入可配置的局部修正规则；不默认对所有模型套用固定角度。

### 交付物与完成条件

交付具体缺陷修复、新开发包、适用范围及修复前后对照。问题条目记录“已复现、已定位、
已改代码、已在当前版本实机确认”中的实际状态。有限矩阵、无报错或某条规则执行过，
都不能单独关闭视觉缺陷。

## 4. 阶段 B：补齐日常游玩的渲染衔接

在阶段 A 的阻断问题收敛后，优先处理真实使用中缺少的衔接代码：

| 开发方向 | 具体工作 | 可交付的行为 |
| --- | --- | --- |
| 切换与打断 | 统一覆盖进入/退出、受击打断、暂停恢复、视角切换时的已显示姿态交接 | 回到 EF 或换动作后不遗留旧姿态，不重新推进退出的物理 |
| 第一人称 | 核对视图变换、身体/手臂显隐、姿态快照所属空间及状态隔离 | 世界第三人称、第一人称和物品栏预览互不污染 |
| 持物与装备 | 补真实问题涉及的手部定位、双手物品、盾、弓弩及装备层衔接 | 手部、武器、模型自带道具和装备使用同一帧的最终姿态 |
| 运动朝向 | 收敛游泳、水中停留、爬行、飞行和梯子的首帧及返回路径 | 不重复施加整体旋转；空覆盖保持 EF 朝向 |
| 生命周期 | 补模型切换、资源重载、重生、换世界和实体卸载后的释放与恢复 | 旧控制器、过渡、查询、物理和可见性状态不泄漏到新实例 |

完成条件是这些衔接在声明支持的环境与模型中正常使用，失败路径可解释、可回退。
具体观察入口以阶段 A 的实际反馈为主；必要的多人与生命周期检查集中到候选版本进行。

## 5. 阶段 C：扩大控制器和脚本支持范围

现有原生槽位接入和共享采样已经实现，后续不再把它们重复列作待开发项。

1. 整理“已支持、部分支持、明确拒绝”的控制器、查询与脚本能力表，运行时提示对应限制。
2. 根据实际模型需要补齐状态图和表达式子集。需要支持控制器引用控制器时，先实现有界依赖图、
   循环检测、深度/操作预算和共享实例语义，禁止直接递归执行无界模型输入。
3. 收敛脚本驱动的开始、暂停、停止、恢复、清空、重激活与 JSON 状态之间的交接，
   维持每个实体和视图的状态独立。
4. 对声音、粒子和同步输出单独设计明确的输出所有权和去重机制。接通之前保留现有抑制策略，
   不能因选中一个姿态来源就重复触发模型效果或网络输出。
5. 对新增能力提供最小示例和明确的失败原因；未知名称继续报告，不用默认零值冒充已经支持。

交付按能力增量的小版本，说明哪些真实模型需求得到解决。是否扩展某个可选集成，
由实际使用需求和官方公开接口决定，不把所有第三方模组列成当前版本的必做目标。

## 6. 阶段 D：让预览器更接近排查与制作工具

### D1：加强报告与对照

- 在现有单帧查看上，增加按需开启、时长和容量有界的短段记录，保留异常前后的切换过程。
  避免日常游戏中持续复制所有骨骼矩阵。
- 显示所选规则、实际基础动作、额外层、控制器状态、时钟、骨骼范围和不支持的输入。
- 补必要的查询、变量、控制器代次、物理输入/状态及随机状态记录；无法取得的字段保留“缺失”。
- 增加记录帧与重新计算结果的对照，区分骨骼姿态、可见性、模型资源和摄像机导致的差异。

### D2：逐步支持受约束的过程回放

先定义输入、状态和坐标空间都可取得的回放范围，再实现该范围内的过程重建。
保留现有 schema 1 单帧查看；只有不兼容的格式变化才升级相应格式版本，并明确拒绝或迁移旧格式。
第一人称、装备、光影或物理历史没有重建时，界面明确标注，不显示“完整还原”。

交付结果是能定位差异的工具，而不是只显示“所有数值有限”。预览器不自动修改游戏配置、
上传问题记录或分发用户模型。

## 7. 阶段 E：降低动作配置成本

- 在外部工具中增加规则编辑入口：选择条件、覆盖来源、额外层、骨骼/通道、权重与时钟。
- 从当前模型和资源中列出可选片段、控制器及骨骼，预览条件冲突、优先级、来源缺失和共享时钟限制。
- 继续使用模组的实际规则解析和计算结果，不在界面里另外实现一套选择逻辑。
- 提供可导入/导出的配置和资源包模板；模型专属预设注明适用模型与资源版本。
  导出位置由用户选择，不能覆盖原模型、存档或未经选择的游戏配置。

现有 JSON 配置始终可直接使用。图形编辑器属于易用性改进，不阻止先交付阶段 A/B 的修复。

## 8. 阶段 F：维护性、性能与发布收敛

- 根据真实记录定位计算、分配、缓存或 GPU 上传热点，再优化；保持动画速度、帧所有权及物理时钟语义。
- 在行为稳定后，将过大的动作合成类逐步拆为规则求值、原生槽位、共享采样与姿态数学等职责，
  每次保持一个可交付的行为边界，避免同时重写整条渲染链。
- 对模型容量、脚本预算、资源重载、缓存损坏和可选依赖缺失提供有界失败和可恢复路径。
- 对接近可用的固定候选包，集中补正式验收所需的实机、多人、长时间运行及性能证据。
  继续遵守[正式验收标准](acceptance-mc1.20.1.zh-CN.md)，不因计划推进而自动勾选通过。
- 达到声明范围后再决定发布内容。正式版本由用户决定；不自动发布稳定版，不自动扩展 Minecraft 目标。

## 9. 执行与交付方式

**用户负责正常游玩时指出不对的地方；开发侧负责采集、定位、修改和解释结果。**

- 每轮先确定具体功能或缺陷，给出代码改动和可使用开发包；不能用增加测试数量代替补功能。
- 针对可独立验证的行为，只增加能发现真实错误的检查；通过后不反复重跑无关检查。
- 需要独立检查时优先交给 LunaMax，自主完成并返回最终结果；主任务不轮询它的中间状态和日志。
  若独立任务因额度或前置条件失败，明确交回失败结果，再由主任务接手必要检查。
- 构建前先确认可用的工具链与兼容依赖来源；网络查询失败应有明确退出和接续方案，避免长期重复等待。
- 每份交付分别写清已实现、针对检查通过、实机已确认及仍未知的部分，关联源码提交和 JAR 摘要。
- 新增测试/运行数据放在用户允许的位置，避免新增 C 盘测试数据；D 盘未获工作区写入权限时，
  先使用现有获准工程目录，不修改全局权限或擅自搬迁原游戏实例。
- 只提交对应任务的源码和文档；运行日志、记录、用户模型及游戏存档留在仓库提交之外。
  GitHub 推送按照会话中明确授权的远端与分支执行。

## 10. 下一轮可直接开始的工作

1. 以 alpha6 为当前体验基线，接收最先发现的真实异常；若 F9 在客户端保存失败，先修采集入口。
2. 优先定位游泳抬头时的头发问题和仍存在的手臂/持物错位，记录实际生效的片段与骨骼链。
3. 交付对应的最小修复与前后对照，再继续阶段 B 中尚有缺口的衔接代码。
4. 没有新阻断反馈时，从能力表、记录帧对照或规则编辑器中选择一个独立增量推进。

不预先承诺某一天“全部完成”，也不把不同模型的兼容数量换算成未经证实的完成百分比。
阶段顺序可根据实际反馈调整；每轮应能说明新增了什么可用行为、解决了哪个问题、还缺什么证据。
